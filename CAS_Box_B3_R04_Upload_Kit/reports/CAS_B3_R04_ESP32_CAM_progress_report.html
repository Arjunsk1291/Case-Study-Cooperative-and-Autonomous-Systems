CAS Box B3 / Rover R04

ESP32-CAM Development and Progress Report

Scope: ESP32-CAM capture, wireless camera service, camera-to-main-box integration, image persistence, metadata, and testing.

Excluded: main ESP32 power, rover movement, partition, and general Wi-Fi failure investigations.

Prepared from the repository history, source changes, serial output, session events, and camera test observations.

1. Camera Goal

The camera goal was to make the enclosed ESP32-CAM operate without physical button access and provide original JPEG images wirelessly to the phone-first investigation dashboard. Each captured image had to be saved by the phone, indexed, and traceable to the investigation timeline and nearby sensor data.

Required outcome

  • Software-only camera control and capture.
  • Original JPEG preservation, not browser screenshots.
  • Frame IDs, timestamps, sizes, status, and failure records.
  • Reliable operation while telemetry and heartbeat continue.
  • Camera disconnection must not destroy already-recorded data.

2. Original Camera Role and Constraints

3. What We Implemented

3.1 CameraStation changes

  • Removed the active dependency on the old laptop upload path.
  • Kept the camera as a wireless snapshot server.
  • Added software registration with the main box.
  • Added JPEG frame serving through the camera HTTP interface.
  • Changed frame acquisition toward PSRAM-aware buffering.
  • Changed capture behavior to prefer CAMERA_GRAB_LATEST so stale buffered frames are avoided.
  • Added a warm-up period of approximately 2–3 frames before normal capture.
  • Enabled automatic exposure and gain controls, including AEC2 where supported.
  • Added the missing write(uint8_t) implementation to FrameBufferStream, resolving the abstract-class compilation error.
  • Removed unreachable code after the active camera path.

3.2 Main-box relay changes

  • Replaced the blocking camera fetch in the AsyncWebServer request path.
  • Moved the camera fetch into a separate FreeRTOS task.
  • Added a bounded cached-JPEG buffer on the main box.
  • Changed the request flow so /camera/snapshot can return 202 while capture is pending.
  • Added a cached-frame endpoint so the phone can poll for completion.
  • Added JPEG start/end validation using the expected FF D8 and FF D9 markers.
  • Avoided the previous large String/lambda copy path for image transfer.

4. Phone Dashboard Contributions

  • Separated heartbeat timing from telemetry polling.
  • Camera status is polled less frequently than the heartbeat.
  • Camera capture is not awaited inside the heartbeat path.
  • Images are treated as saved files/blobs, not merely as a displayed preview.
  • Frame metadata is intended to record frame ID, filename, capture/receipt timing, byte count, status, and missing-frame events.
  • The phone stores camera data in the investigation record and includes it in ZIP finalization.
  • A wake lock was added to reduce timer throttling during a run.
  • Camera failure events are recorded separately from rover and telemetry failures.
Contribution: the camera path was redesigned from a synchronous preview-style request into an asynchronous capture, cache, poll, validate, and persist workflow.

8. Camera Data Model We Were Working Toward

Each image must be more than a file. It must be a traceable camera record.

FieldPurpose
frame_idUnique identity for the captured frame.

capture_timestampCamera-side capture time where available.

sequence_numberOrdering and gap detection.

nearest_sensor_sequenceLinks the image to nearby LiDAR/IMU/GPS/ultrasonic data.

event/segment referenceConnects the frame to notes, route segments, and operator decisions.

9. What Worked and What Did Not

Worked or materially improved

  • The camera compilation blocker was identified and corrected.
  • The camera architecture was clarified as a separate wireless snapshot server.
  • The old blocking relay design was identified as unsafe for heartbeat-sensitive operation.
  • The source was changed toward asynchronous capture and cached-frame serving.
  • Frame freshness, PSRAM use, warm-up, exposure, gain, and JPEG validation were addressed in code.
  • The phone workflow was aligned with persistent image storage and frame manifests.

Not yet proven

  • Stable wireless registration and reconnect under the actual enclosed hardware.
  • Successful image transfer through the complete camera → main box → phone path.
  • Absence of FB-OVF during a sustained run.
  • Brightness improvement under the real outdoor/indoor lighting conditions.
  • 95% or better valid-frame rate.
  • Every frame’s sensor/event linkage in a completed ZIP.
Important: source implementation progress is not the same as hardware acceptance. The camera work is substantially implemented, but the required capture soak and end-to-end evidence remain outstanding.

10. Next Camera Tests

  1. Start the enclosed camera and verify software-side registration only; no button access required.
  2. Request one capture and confirm the phone receives a non-empty JPEG with valid FF D8 ... FF D9 markers.
  3. Repeat at least 20 times while telemetry and heartbeat polling continue.
  4. Run the full 100-capture soak at the planned 3–5 second cadence.
  5. Record requested, received, valid, missing, retried, stale, and corrupted counts.
  6. Record frame age, byte sizes, camera status, and exposure/brightness metadata.
  7. Check for FB-OVF and camera reconnect messages in serial output.
  8. Export the investigation ZIP and verify every saved JPEG has exactly one manifest row.
  9. Check that missing frames are explicitly reported rather than silently omitted.
  10. Only after these tests, tune cadence, JPEG quality, exposure, and retry limits.

11. Final Camera Status

The project contribution this week was the design and implementation of a phone-first, software-controlled ESP32-CAM capture pipeline. We investigated the original failures, corrected the camera compilation issue, addressed stale/overflow-prone capture behavior, enabled automatic exposure controls, separated image transfer from heartbeat-sensitive requests, and designed traceable image persistence.

The main remaining camera objective is empirical validation: prove that fresh original JPEGs can be captured repeatedly, transferred wirelessly, saved by the phone, and reconciled with the frame manifest and sensor timeline. No camera vision or autonomous pillar/route logic was added.

Executive summary

The intended system is phone-first: the phone performs the live investigation workflow, stores telemetry and original camera images locally, records operator decisions, and creates a ZIP. The main ESP32 remains the only live rover hub. The AI-Thinker ESP32-CAM is a wireless snapshot server. Rover firmware was not modified.

The decisive diagnostic result is that the current failure is not a partition-size or application-watchdog problem. The connected ESP32 is correctly identified as an ESP32-D0WD-V3 with 4 MB flash. The partition table is valid and the application fits. Two independent flash reads matched. A minimal Wi-Fi-only firmware reached POWER_TEST_START when explicitly built for 40 MHz flash, then immediately reported Brownout detector was triggered. The blocker is power/voltage or board-level at Wi-Fi startup.

4. Main relay and phone UI

Blocking defect

The original /camera/snapshot handler performed HTTPClient with an approximately 1.8-second timeout, called getString() and constructed a JPEG String inside an asynchronous server handler. This could stall /values, /autonomy?hb=1 and turn requests, matching observed heartbeat safety stops around captures.

Fix

The replacement uses a bounded JPEG buffer, a FreeRTOS fetch task, FF D8/FF D9 validation, immediate 202 response and a cached frame endpoint. Camera work is separated from heartbeat and telemetry.

UI additions

  • Heartbeat interval 500 ms and camera status interval approximately 3 seconds.
  • Screen Wake Lock and hidden-tab event.
  • Drive button selection disabled/touch behavior constrained.
  • Preflight checks for LiDAR, IMU yaw, camera online and safety latch.
  • PILLAR, TURN 90 RIGHT, NOTE and CLEAR SAFETY STOP controls.
Known gap: compact logging is not yet proven to meet the complete final schema, archive verification, ground-truth form, sequence reconciliation and outage recovery requirements.

What upload verification means

esptool verified every written region. That proves USB transfer to flash, not stable execution under Wi-Fi current load. The later brownout demonstrates the distinction.

40 MHz discovery

Initial default builds showed changing checksum/read failures. A minimal sketch explicitly built at 40 MHz reached POWER_TEST_START, so forcing 40 MHz is required. At 40 MHz the remaining failure is a clean brownout at Wi-Fi startup.

7. Serial evidence

Initial checksum failure

rst:0x7 (TG0WDT_SYS_RESET), mode:DIO, clock div:1, changing csum err:0x59!=0x98 and invalid load values. Changing checksum bytes are consistent with unreliable flash reads or flash-frequency mismatch, not a normal application watchdog.

Brownout failure

entry 0x4008059c followed by E BOD: Brownout detector was triggered and rst:0x3 (SW_RESET). This means the boot/application path progressed farther, but supply voltage fell below the brownout threshold. The screen not lighting and AP not appearing follow from repeated resets.

Minimal isolation

POWER_TEST_START followed by brownout. The minimal sketch does not initialize LiDAR, IMU, GPS, ultrasonic, display, RoverLink or WebHMI. Those components cannot explain this isolated failure at Wi-Fi startup.

8. Sensor logging, GPS and drift

GPS

Sensors::toJson() includes GPS state from TinyGPSPlus on Serial2 GPIO16/17 at 9600 baud. The phone logger stores the full /values response in each telemetry record while logging. Fields include fix, satellites, HDOP, latitude, longitude, age, altitude, speed, course and validity indicators. Invalid/stale fixes are not replaced with zero coordinates.

FieldIntegrity rule
fixOnly true means location currently valid
lat/lonUse only with valid fix
age_msDetect stale source data
hdop/satsReport supplied quality; do not infer unsupported precision

Continuous logging reality

Current browser sampling is approximately every 500 ms. Wi-Fi loss, browser suspension, camera work or AP failure can create gaps. A final recorder must reconcile sequences, timestamps, received/written/dropped counts and recovery events. No hardware no-gaps acceptance run was completed.

Drift

IMU yaw can correct heading with bounded opposite wheel offsets. Commanded velocity is not measured velocity without encoders. LiDAR wall distance and valid GPS can provide external references. IMU integration alone cannot guarantee lateral position. No before/after drift numbers were obtained, so closed-loop drift correction is not proven.

ESP32-CAM Edge Computer-Vision Development Report

Correct project objective: run computer vision directly on the AI-Thinker ESP32-CAM without a server, laptop, or full OpenCV installation.

The ESP32-CAM should capture a small grayscale image, perform native/optimized edge processing, estimate the path or lane centre, calculate a lateral offset error, and send a compact result to the main ESP32 navigation controller.

2. Why Resolution and Native Processing Matter

Full OpenCV is unsuitable for the ESP32-CAM memory and CPU budget. Canny-style processing needs image storage for grayscale pixels, blurred pixels, gradients, magnitude, direction, non-maximum suppression, and hysteresis. A 640×480 image contains 307,200 pixels before multiple working buffers are allocated.

ModePixelsReason
QQVGA 160×12019,200Safest starting point for several working arrays and fast control updates.
QVGA 320×24076,800More spatial detail, but higher RAM, CPU, and latency cost.
VGA 640×480307,200Not appropriate for simultaneous multi-buffer native Canny on this target.

The correct first implementation is a bounded region of interest, grayscale capture, small fixed-size arrays, integer arithmetic where practical, and a reduced output packet rather than transmitting a full processed frame for navigation.

3. Proposed Native Vision Pipeline

  1. Capture a QQVGA or QVGA grayscale frame from the camera.
  2. Select a lower image region of interest where the ground/path is expected.
  3. Apply a small blur or local smoothing step to suppress camera noise.
  4. Calculate horizontal and vertical intensity derivatives.
  5. Calculate approximate gradient magnitude and direction.
  6. Suppress weak/non-local maxima or use a simplified thresholded edge map.
  7. Use hysteresis-style strong/weak edge selection if memory and timing allow.
  8. Accumulate edge pixels by column or row.
  9. Estimate the path/lane centre from the edge distribution.
  10. Calculate offset_error = detected_centre - image_centre.
  11. Attach confidence, frame sequence, timestamp, and validity state.
  12. Send only the compact result to the main ESP32.
Important design boundary: the first reliable milestone is a measurable centre/error result. Full image display and advanced vision can remain diagnostic features and must not block the control loop.

ESP-NOW is suitable for a compact low-latency result if the boards can be configured with stable peer identity and channel coordination. UDP is simpler when both devices are already on the same Wi-Fi network. The choice must be tested; no communication method should be claimed as complete before packet-loss and latency measurements exist.

5. Main-ESP32 Sensor Fusion and Drift Correction

The camera provides a visual path error, not absolute rover pose. The main ESP32 must combine it with its sensor-rich state.

  • IMU yaw hold remains the fast heading stabilizer.
  • LiDAR provides wall/obstacle geometry and front-stop evidence.
  • Ultrasonic sensors provide independent near-field obstacle confirmation.
  • GPS supplies outdoor position only when its fix is valid.
  • Vision offset provides a lateral path cue when confidence is adequate.
  • Wheel velocity commands are adjusted asymmetrically to reduce sideways drift, even without wheel encoders.

Example bounded correction:

correction = clamp(K_yaw * yaw_error + K_vision * vision_offset, -MAX_CORRECTION, +MAX_CORRECTION)
left_command = base_speed - correction
right_command = base_speed + correction

Invalid, stale, low-confidence, or missing camera results must be logged and excluded from correction. The system must fall back to the approved sensor/safety behavior rather than fabricate a visual error.

9. Next Implementation Sequence

  1. Add a standalone QQVGA grayscale capture test.
  2. Add fixed-size grayscale and gradient buffers.
  3. Implement thresholded Sobel/Canny-style edge detection.
  4. Log processing time, free heap, PSRAM, edge count, and confidence.
  5. Draw or transmit a diagnostic centre/error result.
  6. Implement and checksum a compact camera-to-main packet.
  7. Make the main ESP32 accept vision only when packet age, checksum, and confidence are valid.
  8. Fuse vision error with IMU yaw correction using named bounded constants.
  9. Run bench tests with the rover lifted, then straight-line drift tests.
  10. Only after measured results, consider wall/path or lane behavior.

Final objective: an enclosed AI-Thinker ESP32-CAM independently extracts useful visual geometry at the edge, while the main ESP32 combines that result with its sensors and safely controls the rover.
